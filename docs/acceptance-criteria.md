# RustOS Acceptance Criteria

_Last reviewed: 2026-10-14._

This document defines the acceptance gates for full-kernel userspace execution,
QEMU validation, fault recovery, writable filesystem and IPC behavior, fuzzing,
and syscall benchmarking. These criteria are requirements, not claims that the
features are already implemented.

## 1. Full-kernel boot and userspace execution

### Required implementation

- Implement ELF image replacement. Validate ELF headers and program headers,
  reject malformed, truncated, unsupported, overflowing, or out-of-bounds
  images safely, map each `PT_LOAD` segment with correct permissions, zero-fill
  BSS, copy user arguments and environment safely, and construct an
  ABI-compliant aligned initial stack with the required process-entry data.
- Ensure failed `execve` leaves the original process image runnable and a
  successful `execve` does not return to the old image.
- Implement architecture-aware process entry and return-state setup. A
  fork-compatible clone must create a distinct child that can be scheduled in
  user mode on every supported architecture.
- Keep minimal and diagnostic boot profiles separate from the full-kernel
  userspace-execution contract.

### Acceptance criteria

- Malformed, truncated, unsupported, and out-of-bounds ELF inputs fail safely
  without kernel panic or memory corruption.
- `PT_LOAD` mappings have the expected address, size, and permissions, and
  BSS bytes are zeroed.
- Invalid user pointers and excessive or invalid argument/environment vectors
  fail safely.
- A failed exec leaves the caller able to continue; a successful exec begins
  at the new image entry point and does not return.
- Process creation and exit assertions execute on x86_64 and AArch64, and on
  RISC-V 64 only when that architecture is included in the supported build
  matrix. Architecture coverage must not be silently skipped.
- Under the full-kernel QEMU path, init executes `/smoke`, waits for that exact
  child PID, and verifies normal termination with exit status zero.
- Each supported architecture passes the end-to-end execution gate separately.
  Minimal boot, diagnostic output, compilation, source inspection, and marker
  string presence do not satisfy this gate.

## 2. Real QEMU gate and artifacts

### Required implementation

- Make `cargo xtask smoke` enforce a bounded deadline, terminate QEMU on
  timeout, clear stale logs before each run, and parse the actual serial log
  generated by that run.
- Write machine-readable JSON metadata for architecture, build/profile and
  QEMU configuration, start/end or elapsed timing, result status, timeout
  state, and artifact/log paths.
- Preserve serial logs, metadata, and relevant failure artifacts on both
  success and failure.

### Acceptance criteria

- A timeout, panic, missing or malformed metadata, missing log, incomplete
  protocol, or failed child status fails the gate.
- The parser rejects stale-log reuse, missing or duplicate required markers,
  a wrong child PID, signal termination, nonzero exit status, and incomplete
  execution sequences.
- Boot timing markers are distinct from userspace execution records. The gate
  requires successful exec, a wait result for the exact PID, normal termination,
  and exit status zero.
- Idle-loop text, marker aliases, or a success-looking line without the
  complete child protocol cannot pass.
- Automated tests cover stale logs, missing and duplicate markers, wrong PID,
  signal termination, nonzero exit, timeout, malformed metadata, and missing
  artifacts.
- Each architecture's actual QEMU run and its artifacts are reported separately.

## 3. Fault recovery, writable filesystems, and IPC

### Required implementation

- Add catalogued fault scenarios with stable identifiers and explicit
  fired/recovered markers.
- Add real guest workloads for writable filesystem operations and IPC send and
  receive. Validate operation results and content, not just that a syscall
  returned.
- Keep fault-integration CI non-gating or disabled until it executes a real
  harness. A readiness guard alone is not a test.

### Acceptance criteria

- Each fault scenario proves that the intended fault fired, recovery completed,
  and a follow-up operation demonstrates the kernel remains usable.
- Guest tests create, write, read, rename, and unlink a regular file, verify
  contents and status, and verify the removed path fails with `ENOENT`.
- IPC tests send and receive actual data and validate the received contents,
  result codes, and process exit status.
- Logs and metadata for failed scenarios are retained for diagnosis.
- Documentation distinguishes implemented tests from planned scenarios and
  does not describe a readiness guard as runtime coverage.

## 4. Fuzzing

### Required implementation

- Add `cargo-fuzz` harnesses that call production parsing and resolution code
  for CPIO/newc archives, ELF images, VFS path resolution, and filesystem
  metadata. Do not replace production logic with duplicate test-only parsers.
- Add minimized seed corpora containing valid, malformed, truncated,
  boundary-sized, and adversarial inputs. Add dictionaries where useful.
- Run bounded fuzz campaigns in CI and sanitizer campaigns where supported by
  the target and toolchain.

### Acceptance criteria

- Each harness builds and reaches the production code path it claims to test.
- CI runs with a fixed, bounded budget and reports unsupported sanitizer or
  architecture combinations explicitly rather than silently skipping them.
- Crashes and failing inputs are retained as artifacts. Every confirmed crash
  is minimized where practical and committed as a regression test.
- Fuzzing status is reported per target, with the executed command, duration,
  and result. Merely having a harness file is not a passing fuzz gate.

## 5. Userspace syscall benchmark

### Required implementation

- Provide a freestanding no-libc workload with explicit warmup and fixed
  measured iterations, per-operation counts, and machine-readable JSON output.
- Include latency distribution statistics and host, guest, architecture,
  compiler, build/profile, and QEMU metadata needed to compare runs.
- Keep baseline comparisons like-for-like and document the reproducible
  collection command.

### Acceptance criteria

- Warmups and measured iterations are reported separately and measured
  operation counts match the configured run.
- JSON output parses and includes the required latency distribution and
  environment metadata. Failed or incomplete runs cannot be reported as
  successful measurements.
- Baseline and candidate measurements use matching workload, architecture,
  build/profile, and environment settings.
- Collect repeated successful runs and characterize variance before approving
  a baseline. Performance thresholds remain advisory until that review is
  complete; no improvement is claimed from a single run.

## 6. Completion and reporting rules

- Map every criterion to an executable test, a reproducible manual test, or an
  explicitly documented automation gap.
- Report build, unit/parser tests, QEMU runtime, fault recovery, filesystem/IPC,
  fuzzing, and benchmark results as separate categories. Do not let a pass in
  one category imply a pass in another.
- Update `docs/status.md`, `docs/milestones.md`, and CI coverage documentation
  only when the corresponding executable gate exists and its result supports
  the status being reported.
- Mark a milestone complete only after its required executable gate passes.
  Source inspection, successful compilation, marker-string checks, and
  readiness guards are insufficient evidence of runtime behavior.
- Document prerequisites, exact reproduction commands, architecture coverage,
  known limitations, and artifact locations for each gate.

## Current implementation status

These criteria are acceptance requirements, not evidence of completion. The
full userspace execution gate remains blocked while the kernel's process
creation, ELF loading/image replacement, user-mode entry, and exact-child
reaping path is incomplete. Consult [Subsystem Status](status.md),
[Product Milestones](milestones.md), and the [Userspace Smoke Runtime
Contract](userspace-smoke.md) for the current implementation state.
